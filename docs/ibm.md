# IBM Runtime

<a id="ibm-runtime-execution"></a>`IBMRuntimeBackend` runs NWQLib's circuits on an IBM Quantum device through Qiskit IBM Runtime. Install the `ibm` extra, construct a connection for your device and instance, and run with the steps in [Run on any backend](backends.md#run-on-any-backend). The example below is a template and is not run here, because it needs an IBM account:

```python
from nwqlib.backends import IBMRuntimeBackend

backend = IBMRuntimeBackend(device="YOUR-IBM-DEVICE", instance="YOUR-IBM-INSTANCE")
```

The configuration cannot change after construction. Offline SDK and transport checks do not qualify a live account, queue or QPU.

The backend returns sampled counts through the client-side SamplerV2 of qiskit-ibm-runtime, and a provider expectation estimate through its client-side EstimatorV2 when the Method requests one, as `ExpectationMethod(estimate_precision=...)` does. These primitives build each job on your computer and send it to IBM's `executor` program, and when the Run reads the job they turn the returned result into counts or estimates on your computer. The `ibm` extra requires qiskit-ibm-runtime 0.52.0 or later, the first release whose top-level `SamplerV2` and `EstimatorV2` are these primitives ([Dependency issues](dependency_issues.md#qiskit-ibm-runtime)). The backend rejects exact readouts, which a simulator computes from the state with `shots=None`, without shot sampling and subject to numerical rounding, and trajectory readout, which reads several points of one simulated evolution, before contacting the service.

NWQLib's error budget, the error bounds and checks that it reports as [error evidence](glossary.md#error-evidence), covers only NWQLib's own computation. It excludes what the IBM SDK and service do to a job, such as error mitigation, twirling, the processing of observables and shots and the uncertainties they report, and it excludes hardware error. NWQLib keeps the returned counts and estimates without correcting them, and [Client-side primitives](dependency_issues.md#client-side-primitives) lists the SDK behavior that changes them.

## Credentials

The constructor reads no credentials and does not contact the service. Preparing or refreshing a run loads the SDK and its credentials. With `account_name`, the backend uses that saved SDK account. Otherwise it reads the environment variable named by `token_env`, by default `NWQLIB_IBM_RUNTIME_TOKEN`. Secrets are not saved in the run's records.

## Submit and wait {#ibm-runtime-prepared-execution}

Pass the connection to `nwqlib.prepare(plan, backend=backend, directory=...)`, call `nwqlib.submit(prepared)` and continue through the returned run. [Save and reopen pending work](run_archives.md#save-and-reopen-pending-work) shows how to save that run and reopen it later. Job mode is the default. `mode="batch"` or `mode="session"` attaches every job to the existing Batch or Session whose ID you pass as `container_id`.

Preparation transpiles to the device's instruction set and keeps the logical-to-physical layout, the effective primitive options, the SDK versions and the [native two-qubit depth](#native-two-qubit-depth) of the compiled circuit. The effective options are the requested `options_json` with the defaults that preparation writes in, resilience level 0 for an estimate and an explicit `false` for each unset dynamical-decoupling or twirling option of counts, and every job of the preparation is built with them. The client-side primitives apply the twirling, dynamical-decoupling and mitigation options on your computer while they build the job, and the metadata of an Estimator job, which each estimate saves, reports the options that the Estimator applied. The default `optimization_level` is 1, and the [rules shared by all backends](backends.md#optimization-level) apply.

The preparation of each experiment refuses these options before that experiment is submitted:

- `environment.private=true`. IBM returns the result of a private job only once, so a Run could not read it again after a failed or interrupted retrieval. Leave the option false.
- Gate or measurement twirling of counts, unless `options_json` sets `twirling.num_randomizations` and `twirling.shots_per_randomization` to integers whose product is the shots of each experiment, such as 16 and 64 for 1024 shots. Otherwise the Sampler chooses the split itself and can return another number of shots ([Client-side primitives](dependency_issues.md#client-side-primitives)). One `options_json` holds the split for every experiment of a Run, so a Run whose experiments request different shots cannot twirl its counts. With `PencilSampling` of FixedGCIM, ADAPT or QFD, the results of the pilot stage decide the shots of the main stage, so the refusal can come after the jobs of the pilot stage have run.

The SDK can also refuse a request while it builds the job, which happens after the Run has recorded the submission. No request reaches IBM, so no job runs and nothing is charged. NWQLib cannot tell such a refusal from a failure after the request was sent, so the submission stays uncertain, its work stays counted and it is not submitted again. The SDK's error message describes the refusal. Change the options or the observable and start a new Run of the Plan ([Interrupted attempts](run_archives.md#interrupted-attempts)). With qiskit-ibm-runtime 0.52.0, for example, the Estimator refuses in this way zero-noise extrapolation with `resilience.zne.extrapolator` set to `"double_exponential"` and the default three noise factors, and probabilistic error cancellation with `resilience.layer_noise_model` unset.

The run folder keeps each circuit as QPY (Qiskit's binary circuit format) before submission, so a prepared but unsubmitted circuit survives an interruption. Before the Run keeps those bytes, it compares their number with what is left of `max_data_bytes`, and twice their number, for the two copies held in memory while they are written, with the Method's `max_bytes` or the physical memory of the computer. The second comparison is a coarse estimate and not a bound on process memory, and Qiskit has already serialized the circuit by the time this comparison runs. Either refusal leaves the preparation counted without a record. After a data limit, `run.extend_limits(max_data_bytes=...)` and `run.resume(rebuild_preparations=True)` finish the same Run without repeating a job ([rebuild an interrupted preparation](run_archives.md#rebuild-an-interrupted-preparation)). Later retrieval uses the original job and does not serialize the circuit again, and resuming a known job uses its original job ID without recompiling or submitting another job. The saved QPY circuits have ordinary local IDs and keep their saved bytes. They are not content-hashed or authenticated, and editing them does not trigger a check of the archive's mathematical assumptions. Jobs already submitted and their returned results still describe their original executions. A failed retrieval records the original job state and raises the original exception with its traceback, and a later explicit refresh can retrieve the same job. Errors in decoding a result are raised and are not treated as a pending job. When NWQLib fails to decode one PUB of a job (primitive unified bloc, a circuit with its parameter values and its shot count or precision, the unit of input of an IBM primitive), the PUBs decoded before that one stay saved. The SDK, however, turns the whole returned result into counts or estimates in one step when the job is read, so an error in that step leaves no PUB of the job decoded, and each later read repeats that step.

## Circuits that differ only in angles {#ibm-templates}

A Run of a static Plan, whose settings are all fixed before running, prepares one circuit for each experiment, or, for an experiment whose `MeasurementBatch` has range axes (`RangeAxis`), one circuit for each combination of axis values, such as each row of `LCHS(estimator="sampled_pairs")`. When these circuits return counts, differ only in rotation angles and share one readout, shots included, as those rows do, preparation compiles one template circuit with those angles as parameters for each group with the same gates. One job then sends all unsubmitted circuits, each group as one Sampler PUB with one row of parameter values per circuit. Every circuit keeps its own preparation record, with its values in [`PreparedArtifact.template`][nwqlib.execution.PreparedArtifact], its own attempt and its requested shots, which count against the Run's limits. A reopened Run binds the angles of a later circuit to the saved template without compiling again. A Method declares these groups with `Method.row_templates` ([Extending NWQLib](api/extending.md)).

`IBMRuntimeBackend(use_fractional_gates=True)` opens the device with IBM's fractional gates, RX(θ) at any angle and RZZ(θ) with 0 ≤ θ ≤ π/2, and compiles for that device. Preparation refuses a device without these gates and the options that IBM documents as unsupported with them, which are gate twirling, probabilistic error cancellation and noise amplification by probabilistic error amplification (PEA), including Estimator resilience level 2. The compiler cannot fold an RZZ angle that is a parameter of such a compiled circuit into that range, so preparation folds each circuit's angles without compiling again, keeping the unitary and its global phase. The circuits that need the same correction gates then share one folded template and one PUB, so the number of PUBs depends on the angles. With qiskit-ibm-runtime 0.52.0 and samplomatic 0.21.0, the Sampler refuses measurement twirling of these folded circuits while it builds the job, with an error about the shape of `parameter_values`, and the submission stays uncertain ([Submit and wait](#ibm-runtime-prepared-execution)). The [`IBMRuntimeBackend`][nwqlib.backends.ibm_runtime.IBMRuntimeBackend] reference gives the folding rule. The compiled circuits with parameters and the folding were checked offline with the SDK, like the rest of this backend.

## Counts

SamplerV2 returns joint classified counts. Each PUB keeps its original item position, also when one prepared circuit appears more than once. Named classical registers are joined shot by shot before the logical bit order is restored. Each physical circuit execution produces its own set of shots, which by itself establishes neither independence nor stationarity. With twirling, the Sampler combines the shots of all its randomizations into one set of counts. Shots of one randomization can share noise, so counts whose number equals the requested shots still do not establish independent, identically distributed shots, and the intervals that NWQLib computes from them remain conditional on the declared sampling model. Fixed simulator seeds can repeat known data and do not establish independent observations.

Before the registers of one Sampler PUB are joined, `sampler_decode_bytes` in `nwqlib.backends.ibm_runtime` estimates the arrays of joining and decoding them, `S*(9*Q+w+32)` bytes for `S` shots, `w` classical bits and `Q` packed bytes per shot over all registers, and the estimate is checked against the run's `ExecutionLimits.max_data_bytes` ([Engineering constants](ENGINEERING_CONSTANTS.md)). Up to 64 classical bits, the backend returns one uint64 index and one int64 count per distinct outcome. Above 64 classical bits, it returns bit-string count keys, and their Python strings and dictionaries are not part of the estimate. The shared decoder checks either representation against the cardinality of the prepared readout and builds the public count records. This check applies `max_data_bytes` to one PUB at a time, separately from the run's cumulative total of saved data, and does not bound Python object memory, Runtime transport or whole-process memory.

## Native two-qubit depth {#native-two-qubit-depth}

The native two-qubit depth of a circuit is its two-qubit gate depth after compilation to the device's instruction set, including the routing that the compilation adds: the largest number of two-qubit gates on any chain of operations that depend on one another. Preparation records it for each compiled circuit in [`PreparedArtifact.native_depth`][nwqlib.execution.PreparedArtifact]. FixedGCIM, ADAPT and QFD read it when you pass `max_2q_depth=D`. Each circuit is then checked just before its submission, after its preparation, and a circuit whose depth exceeds D, or whose depth is not qualified in the sense below, is not submitted. A FixedGCIM or QFD run then raises `nwqlib.backends.inspection.NativeDepthCapRefusal`, an ADAPT run ends with the stop reason `native_depth_refused` and the last pencil it solved, and in both cases the circuits submitted earlier keep their counts and shots. IBM Runtime is the only backend that computes this depth, so on every other backend an integer limit refuses the first circuit.

A recorded depth is qualified, that is, it is the depth of the compiled circuit that NWQLib submits with no request to change its gates, only when all of these hold:

- The circuit is a counts (SamplerV2) preparation. An Estimator preparation never has a qualified depth, because the provider measures the observable with circuits that it builds from the submitted one.
- The effective options keep `dynamical_decoupling.enable`, `twirling.enable_gates` and `twirling.enable_measure` false, so that the provider runs the submitted circuit without changing its gates. An option set to `true` stays on and leaves the depth unqualified.
- Every operation of the compiled circuit has a known meaning on the device target (`nwqlib.backends.inspection.inspect_native_depth` lists the operations that qualify).

Experiments that differ only in their rotation angles, such as the rows of LCHS `sampled_pairs`, run one compiled template bound to each row's values, or, with fractional gates, one of the circuits folded from it whose RZZ angles lie in [0, π/2]. Every row of such a circuit runs the same gates on the same qubits, so its recorded depth is that of the circuit bound to its first row. It is qualified only when the device accepts every value of each parameterized gate, as it does for a gate without angle bounds and for the folded RZZ gates. Folding adds only single-qubit gates, so the folded circuits of one template have the same two-qubit depth.

An unqualified depth is unknown, never zero, and its reason is recorded in its place. With an integer limit, an unqualified depth refuses the circuit. Without a limit, the default `None`, preparation and execution continue as usual.

The limit also refuses a circuit whose preparation recorded a version of nwqlib, Qiskit or qiskit-ibm-runtime other than the installed one, as after a Run is reopened in another environment. This refusal raises `NativeDepthCapRefusal` with its `provenance` set for every method, ADAPT included, and the Run stays resumable. Reopened where the recorded versions are installed, the Run checks the same circuit against the limit again. A new Run prepared in the installed environment records depths of its own.

## Expectation estimates

For finite-Pauli expectation, `ExpectationMethod.estimate_precision` selects EstimatorV2. NWQLib maps the full weighted observable, including identity terms and every nonzero coefficient, to the circuit's physical layout and passes it to the Estimator, which can then remove terms whose coefficients are at most 1e-8 in absolute value ([Client-side primitives](dependency_issues.md#client-side-primitives)). The returned signed estimate is kept without clipping. The reported `stds`, the `ensemble_standard_error` when the Estimator returns one, the requested settings and the returned metadata are kept separately in each estimate. `EstimateValue.standard_error` holds the reported `stds` only when the request turns zero-noise extrapolation (ZNE) off, with `resilience.zne_mitigation` set to `false` or at resilience level 0 without that option. Otherwise it is `None`, and `uncertainty_unavailable` gives the reason. NWQLib does not verify the statistical interpretation of these values, and its error budget excludes the provider's processing and hardware error. The Estimator sets the shots of each measurement configuration, a group of Pauli terms measured together, from the precision, and `ExecutionLimits.max_total_shots` does not count them, so that limit does not cap Estimator spending. The default resilience level is zero. Other supported options require explicit selection, and experimental overrides are rejected before preparation.

## Retries and cancellation

Every job carries the tag `nwqlib:<submission UUID>`. If its job ID never reaches the run folder, because the process stopped or the launch raised after the request was sent, the submission stays uncertain and its work stays counted, and the next refresh searches for the job. It asks the service for at most two jobs of IBM's `executor` program with that tag on the configured device and instance. Counts and estimates both run as `executor` jobs, and decoding checks which kind each returned PUB holds. One match whose instance, program, device and tag agree with the submission becomes the saved reference to the job. No match leaves the submission unresolved, and two matches raise, because neither case identifies the original job and neither permits a new submission.

A run cancellation stops new work and requests cancellation of each pending job, and later provider status confirms the outcome. Cancellation does not return the jobs or shots already counted. A request that fails is sent again by a later `run.cancel()` or `run.resume()` until the job is recorded as ended, and it does not stop the read of that job, so a result that had already finished is collected. A request interrupted while being sent is not repeated ([Cancel, close and handle failures](prepared_execution.md#cancel-close-and-handle-failures)).

The SDK retries certain 5xx POST responses under IBM's documented safe-retry rules, with at most five retries per HTTP request and at most three connection retries. NWQLib itself never resends a job request. The transport of qiskit-ibm-runtime 0.52.0 was checked through a local HTTP server with the real SDK client, primitive, job and decoder. A lost POST acknowledgement was not resubmitted, the tag lookup recovered the original job, and a read answered first with 503 was retried. These tests establish the behavior of the client, not server billing or hardware accuracy. Internal SDK buffers, the read timeout, compilation memory and total network traffic are not bounded by the backend's metadata limit, and no NWQLib limit bounds the memory that the SDK uses on your computer to build each job and to process its result.
