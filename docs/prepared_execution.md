# Prepared execution

A `Plan` (the selected construction and its costs, computed by `plan(...)` before any circuit exists) owns the original Problem, configured Method, output, scientific settings and randomness. `prepare` creates one `Prepared` object over a live `Run`; `submit` advances that same Run. A pending provider job remains accessible through the returned Run.

The first `submit(prepared)` starts its Run. Calling `submit` again on that same Prepared creates a fresh Run with fresh cumulative limits and the original randomness of the `Plan`. It does not continue the first Run. The original explicit directory is not reused: synchronous local work has no new journal unless separately prepared with a directory, while a remote Run chooses its own durable folder. The same `Plan` seed can reproduce the same sampled stream, so a new Run identity does not establish statistical independence. Continue existing work with the returned Run's `resume()` or `wait()` instead.

In a live notebook, `solve` and `prepare` update one compact progress display. It shows input acceptance, preparation, submission, collected observations and analysis. Preparation and collection counts come from published artifacts and observations; unknown totals remain unknown. Scripts are quiet by default. Use `progress=False` to disable the display, or supply a synchronous `progress(stage, done, total)` callable. Observer failure disables that observer and records a process-local notice in `run.warnings`; it never retries scientific work, draws another seed or resubmits a job. Analysis finishing is an execution stage, not a scientific accuracy claim.

```python
import nwqlib
from nwqlib.algorithms.expectation import ExpectationMethod
from nwqlib.execution import ExecutionLimits
from nwqlib.operators.inputs import ingest_pauli
from nwqlib.problems import Expectation

problem = Expectation(state=[1., 1.],
    observable=ingest_pauli((("I", 1.), ("Z", 1.)), num_qubits=1))
plan = nwqlib.plan(problem, method=ExpectationMethod(), shots=64, seed=7)
prepared = nwqlib.prepare(plan, limits=ExecutionLimits(max_total_circuits=1, max_total_shots=64))
with prepared.run as run:
    nwqlib.submit(prepared)
    result = run.wait()
    print(result.value)
```

Supply `backend=connection` and `directory="my-run"` to `prepare` for a chosen provider and durable folder. Remote execution requires durable state; when no directory is supplied, the Run selects a local folder. Inspect `run.directory`. The selected `Plan` and native payloads are saved before submission. Preparation may itself wait for remote compilation. `run.resume()` retrieves outstanding original work and advances the Method controller; `run.wait()` repeats that operation within its explicit timeout. A retrieval error keeps its original provider locator and propagates to the caller. It does not authorize another submission.

Close the current controller before reopening its same folder:

```python
with nwqlib.load_run("my-run", backend=connection) as run:
    run.resume()
    print(run.exposure)
```

`load_run` requires the matching backend configuration. It restores the saved `Plan`, RNG positions, controller frontier, prepared payloads, existing numerical caches, completed observations and pending submissions. It performs no planning, analysis, circuit lowering or numerical reference reconstruction. `run.save("another-folder")` explicitly copies a returned frontier into a new folder. Saving a completed Result is a separate operation; see [saved results](saved_evidence.md).

The `.nwqlib-cache-` filename prefix is reserved for disposable cache payloads. After an interruption, reopening deletes unpublished files with that prefix under the controller lock, before accounting for stored data. Current inputs and referenced cache files are preserved. Keep user-created files outside this namespace. Recovery covers an interrupted process (an exception, a keyboard interrupt or a killed process). SQLite commits are synchronized, but external input and cache files are written without `fsync`, so the archive does not guarantee recovery after power loss.

`run.data` is an immutable snapshot of actual observations, preparation records, execution trace and kept array handles. Taking a snapshot shares immutable arrays. Completed observations are published once; collection is idempotent. Failed and unused work remains in the trace. `run.exposure` separates `completed`, `reserved` and `uncertain` physical submissions, including circuits, shots, jobs and provider-managed sampling. Its `failed` category applies to confirmed host failures and adds no quantum work. Host invocations and work set aside remain in the trace. A provider estimate does not become a known raw shot population.

The count-likelihood check keeps a Run-owned index derived from actual preparation records and measurement identities. Work already committed and set aside keeps its fixed streams unavailable for another independent sample, even if its result is uncertain or never collected. Completed observations update that index once, and reopening rebuilds it once when the check is next needed. The index is not another serialized observation history and supplies no new independence proof.

When supplied, `run.forecast` and `run.allocation` preserve the selected `PlanEstimate` and `Allocation`. The same immutable values appear in `run.data` and the Result's data and survive save/reopen. The Run validates their original `Plan` and source associations. Before each new submission or host invocation, it binds an existing matching point assessment to `event.assessment_id`. A future adaptive point without a forecast keeps `None`. Neither continuation nor opening a saved Result reevaluates models, changes shots or configures a backend from an Allocation.

`ExecutionLimits` contains finite circuit, shot and stored-data limits, a limit on the amplitude count of each declared direct state preparation that the Run synthesizes (`max_direct_amplitudes=65_536`, checked for the whole `Plan` before the first preparation), a limit on the work of the exact dense-unitary syntheses that the Run makes while it prepares circuits, when a backend lowers a circuit to a gate basis or lowering controls a transformed block (`max_synthesis_work=1_000_000_000`, a total over all preparations, each amount set aside before its synthesis starts, [selected blocks](blocks.md#admission-of-the-exact-synthesis)), plus simulator memory configuration. Basis lowering synthesizes each distinct matrix once per Run object, and a reopened Run synthesizes it and sets its work aside again. These are controls on represented work, not provider billing, process RSS or proven CPU-time bounds. The complete fixed workload is checked against the limits before preparation. Native calls set aside their actual circuits and shots before they start. `run.extend_limits(max_total_shots=128)` sets a new cumulative cap of 128 and does not add 128 shots, reset usage or change scientific settings. Array publication, native payload serialization and journal output count toward stored data.

Every actual increase appends an immutable `LimitAmendment` to `run.limit_amendments`. It records the complete old/new limits, sequence, timezone-aware timestamp and counters immediately before publication: circuit preparations, circuit measurement attempts, explicitly prescribed raw shots, stored data bytes, pending output bytes and the dense synthesis work set aside against `max_synthesis_work`. The record refuses counters that exceed the old limits, counting stored and pending bytes together against `max_data_bytes`. Failed and unused preparations count, and so do set-aside and uncertain measurements. Host work and unknown provider-managed sampling do not become circuit/shot counts. Equal values are a no-op. The new cap and its single history row commit together, and metadata must fit the new data cap. A failed limit check or write publishes neither change. An error message's suggested `max_data_bytes` value covers the transition or gate named in that message. Recording a limit amendment consumes storage, and later writes can require a larger cap. `run.trace` and each Result's data preserve their captured cap/history prefix, so increasing the Run later does not alter an earlier Result.

`run.cancel()` prevents new work, requests cancellation of the original remote jobs and preserves all charged work. A provider status establishes cancellation; a request alone does not. A backend without a cancellation operation, such as local [NWQ-Sim](nwqsim.md), receives no request. The Run adds a notice to `run.warnings`, and an already launched job can still finish and be read by a later `run.resume()` of the same Run. Cancellation cannot preempt an already running synchronous native call. Ordinary resume does not retry an interrupted classical analysis. A Method with a concrete recovery hook can accept `run.resume(reanalyze=True)` to retry that saved controller analysis explicitly. Completed Results use `result.analyze(...)` instead.

Closing a Run releases its private numerical/native caches and controller lock. It preserves the Result, immutable scientific data, preparation records and accumulated charged work. Inspect `prepared.circuits` before closing; those returned circuit copies cannot mutate the actual prepared input.

For a long open durable Run, `run.release_native()` explicitly releases fully collected, inactive prepared native payloads that have existing QPY snapshots. It returns `released` identities and `kept` identity/reason pairs. Currently this restores Aer QPY snapshots; other backends, unsaved objects, unsubmitted work and active controller/pending consumers are kept. Lightweight handles and inspection order remain. Inspecting a released item loads its existing QPY once, without lowering, transpilation or submission; an explicit repeated submission can use that same restored native input. Shared gate definitions needed for future preparations remain cached. These counts describe released native objects, not measured bytes or RSS; user-held native references can keep objects alive. Run archives must remain available for later inspection.

`solve` closes the Run it creates before returning its Result or propagating an error. A failed `prepare` also releases its unreturned Run. Their durable files and original jobs remain available for recovery; closing does not cancel a job. Successful `prepare` and `submit` return a live owner that you close explicitly.

`run.wait()` raises `nwqlib.execution.RunFailed` when an original compilation or execution is confirmed failed or cancelled and the Method has not returned a valid Result. The exception provides `stage`, `status`, `locator`, `failure`, `directory`, and immutable `trace`/`exposure` snapshots. Pending work still uses `TimeoutError` when the requested timeout expires. A retrieval error preserves its original exception and locator; it is not reclassified as a failed job. Available partial results remain the Method's responsibility, and no failure causes an automatic replacement submission.

A synchronous host exception that finishes and is durably recorded has event status `failed`; its original exception propagates from `submit`, and subsequent `wait` or reopening exposes `RunFailed` with the recorded failure. The invocation and work remain charged. Unused output capacity can be released without refunding that work. Process interruption or failure to persist completion remains `uncertain`, and cannot be treated as a completed host failure or retried implicitly.

The output limit check includes the encoded readout declaration, declared numeric values and arrays, the host application records a kernel declares, plus `ExecutionLimits.max_completion_metadata_bytes`, which defaults to 65,536 bytes per completed attempt. This extra budget covers variable provider annotations and undeclared host application records, excluding the already-funded declaration and declared records. A single-endpoint probability readout also spends it on its remaining chunk fields, the manifests and summaries of its largest legal encoding and its publication rows, and is refused before lowering when those known costs exceed it. A trajectory funds each probability point's manifests, summaries and publication rows in the point's set-aside header, so the budget funds each point's job envelope and the completion rows. Increase it explicitly for providers that return larger metadata. A response beyond its selected limit can be rejected after measurement, with its work still charged. Before native preparation, a static Plan on Aer checks the largest known completion-metadata requirement of all its counts, exact Pauli scalar and amplitude settings. Counts reserve the maximum decimal width of the returned-shot count in both the chunk and its completion event. Exact Pauli scalar readouts use the same declaration/value/metadata split. Amplitude endpoints also fund their scalar summaries, physical scale and the larger of the array-publication and declared unavailability branches. These laws are established for Aer. Another backend checks such readouts at publication. A publication failure that has already made a synchronous acquisition terminal cannot be cleared by extending a limit on that Run. Setting bytes aside allocates no output buffer.

If an interrupted attempt has no retrievable outcome, `resume()` and `wait()` raise `RunFailed` with `stage="recovery"` and `status="uncertain"`. This applies to interrupted host kernels and local Aer calls without a recoverable backend job. The error names the original attempt and saved Run. It preserves recorded failure text, observations and charged work. For a reopened synchronous Aer attempt without a job locator (next paragraph), the recorded failure text is the one written on reopening, which states that the in-process result is unavailable. It does not assert that the underlying execution failed. A Method may still return a lawful partial Result before this check. Remote work with a refreshable locator, or a supported reconciliation path to that locator, keeps its pending behavior. The order of the journal writes behind these recovery rules, and what a crash between any two of them leaves behind, is described in [execution contracts](development/execution.md#write-order-and-crash-windows).

When an uncancelled Run reopens an interrupted synchronous Aer attempt with no saved job locator, its in-process result is unavailable. If the Method cannot return a lawful Result from the saved data, both `resume()` and `wait()` raise `RunFailed` with `stage="recovery"`, `status="uncertain"` and the original attempt identity in `attempt`. The exception includes the attempt record in `trace`, the saved Run directory and the charged exposure. Reopening marks the submission `failed` with `results_consumed=True` to record that its output cannot be retrieved, and releases its pending output-byte reservation. The attempt stays `uncertain`, and its job, circuit and shot exposure stays charged. Inspect the saved evidence or cancel this Run. To execute the Plan again, start a new Run. Nothing is resubmitted in the original Run.

By default `prepare` prepares the setting that the Method submits first, which for a static `Plan` is its first experiment, and `submit` prepares each later setting when it reaches it. `prepare(plan, settings="all")` prepares every static setting in `Plan` order and submits nothing, so `prepared.circuits`, `prepared.inspect_resources(index=...)` and [logical compilation](fault-tolerant-resources.md#compile-every-setting-of-a-plan) reach every circuit before any measurement. `prepared.setting_names[i]` is the name of the `Plan` experiment (an entry of `plan.experiments`) that circuit i realizes. Each setting is prepared and charged once, and a durable Run journals it. `submit`, and `resume` of a durable Run reopened after `prepare`, use the saved preparations without lowering them again. A preparation that fails or is interrupted after its charge, other than a refused synthesis, stays charged without a preparation record. The Run never repeats it on its own, so `resume` raises before it submits any further setting, and a new Run prepares the `Plan` again. Both modes draw each setting's runtime seed in `Plan` order, so choosing `"all"` does not change the seeds. The Run checks the whole static population against its limits before the first preparation in both modes, so `"all"` has no limit of its own.

In this version `"all"` needs local Aer, local NWQ-Sim or classical host execution ([open work](ROADMAP.md#preparing-every-setting-on-remote-backends)). Another backend, such as IBM Runtime, IonQ, Nexus or Slurm, is refused before a Run is created, because its preparation can be a remote compilation with a provider charge. The selected construction is the same on every backend, so for counts and exact readouts, preparing on Aer shows the circuit of every setting within `ExecutionLimits.max_simulation_qubits`. RWPE, Lanczos with `SensitivitySampling` and ADAPT set later queries from earlier outcomes (feedback angles, main-stage shots and selected generators), so they refuse `"all"` before a Run is created, and the default prepares the query that their controller submits next.

`prepared.inspect_resources(index=0)` counts the top-level operations of one existing native circuit by name, without copying it. The index follows the order of `prepared.circuits` and `prepared.setting_names`. Its finite `max_operations` and `max_bytes` controls apply to that inspection. Supplying `transpile_options` requests one auxiliary compilation for the selected circuit. That inventory counts the compiled copy, records the effective options and does not replace the executable circuit. Inspection requires an open Run.

Actual compilation follows the configured backend and preparation record. Alternative resource contexts describe estimates and cannot change the circuit being executed. Prepared inventories refer to the effective native compiler configuration and layout. See the [IBM](ibm.md), [IonQ](ionq.md), [Nexus](nexus.md) and [Slurm](slurm.md) pages for their distinct supported readouts and qualification scope.

A bound Aer noise model can select a narrower native gate basis. Counts preparation translates canonical intermediate gates to that actual basis with Qiskit's BasisTranslator, so noise applies to the gates that are executed. The preparation record identifies this translation and the effective native inventory. Exact readouts still require a noiseless backend; raw noisy counts do not establish a bound on physical bias.
