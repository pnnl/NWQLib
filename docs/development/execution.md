# Execution ownership

`_prepared_execution.Run` owns the single prepare/submit/collect lifecycle. The public `scientist.prepare` and `scientist.submit` functions use that same object. Method controllers select their actual next experiment through `Plan.resolve`; backend adapters implement native preparation, submission, retrieval and cancellation. There is no separate controller that reconstructs a request or refreshes spent limits.

Preparation validates the selected realization and filters native block bindings to its exact selected construction. The strict lowering boundary rejects missing or extra identities. Runtime draws come from the saved Run RNG. Compiler options come from the selected backend configuration; resource contexts cannot modify actual lowering or execution. Native receipts keep readout shape, layout, compiler/configuration identity, seed and acquisition provenance. Before native preparation, the Run admits the readout's items and payload bytes (`_prepared_execution._admit_readout`): it subtracts the readout declaration and the completion metadata allowance from `max_data_bytes` and divides the remaining bytes by the readout's statistic stride before forming an item count. A trajectory reserves the sum of its point declarations, fixed chunk headers and representation-specific value payloads, plus one completion-metadata allowance for the acquisition, and before native work each point chunk's job text and empty values envelope, together with the backend's maximum established growth of the acquisition's completion rows, must fit within that allowance. A backend that does not execute a selected trajectory schedule, view or reduction rejects it, naming the backend and the unsupported feature, before the trajectory's readout shape and metadata allowance are checked and before native construction or submission. Before a trajectory's preparation charge, the readout shape check refuses a selected Program with measurement registers, which a measurement needs, and then the selected IR is checked for one coherent evolution along the executed prefix. An explicit reset of a nonempty register, an outcome-dependent branch or an adaptive loop that starts before the last point's boundary, or that appears in the tail or inverse of a readout view, is refused there with a message that names the selected IR. Each selected block lowers to a Qiskit gate, which cannot hold a reset, a measurement or an `Initialize`, and after lowering and before submission the adapter checks the top-level instructions of the lowered circuit. A trajectory receipt records the body length and each point's resolved boundary. The exact statevector target of Qiskit Aer executes a trajectory in one simulation. It inserts every point's saves at the point's boundary in the bound body before lowering, shares one save between identical requests at one boundary, and executes nothing after the last save. Its receipt counts the native evolution operations executed through the final observation, counts no save instruction, and does not multiply that count by the number of labels or points. At a readout view's boundary Aer applies the view's selected tail, the view's saves and, when a later observation follows, the selected exact inverse of that tail. A view executes for Pauli and probability points. Before native preparation, a trajectory's reductions are admitted against the calling Method's remaining work allowance, and its live state, every retained save (probability marginals, expectations and saved states) and the transient marginal workspace against `simulator_memory_mb`, with the thread cap that the simulator is given. On the inherited static path (`Method.prepare` and `Method.execute`) the allowance comes from the Method's `reduction_allowance(plan, point, *, observation, width, run)` hook, which first applies the Method's own limit on the private workspace of its reducers. The static path asks the hook again before it submits an existing preparation, including one that a reopened Run submits, so the acquisition is admitted against the allowance and limits in force at submission.

Before a new original acquisition, the shared submission owner calls `Method.before_submit(plan, prepared_tuple, run=run)` once, before intent and backend work. This applies to a single synchronous handle and a detached batch. Retrieval never repeats this hook. Method owners use it for definition-valid populations: for example, QPE and accuracy-selected finite-Pauli sampling reject known reused fixed streams, including completed unused data and uncertain attempted work. Distinct UUIDs, circuits, seeds or equal histograms do not prove independence.

The complete fixed workload is admitted before its first preparation. Each physical intent then records actual circuits, shots, jobs and provider-managed sampling before execution. A failed call updates the corresponding event and physical submission together. Lost acknowledgements preserve uncertainty and original locators. Refresh retrieves the original job, atomically publishes each successful observation once and keeps earlier successful items if a later item fails. Repeated collection does not duplicate observations or refund exposure.

ExecutionLimits controls actual represented work and stored data. Data admission covers array publication, pending native output, saved native payloads and journal output before those operations. The simulator memory field configures the simulator; it is not whole-process RSS. Provider estimates keep managed sampling separate from raw shot counts. Native execution packets keep their actual evolution population, independent of shot number or MPI rank count.

`Run.extend_limits` writes only the new current limits and one fixed-field `LimitAmendment` in the existing transaction. It snapshots known counters before publication and publishes live limits/history only after success. Equal caps do not write. Each amendment excludes previous history, trace and arrays; its encoded metadata is charged to `max_data_bytes`. The original journal header supplies the initial caps, and restore validates the ordered old/new chain before continuation. A saved completed Result records its captured history length and byte counter, preserving its earlier snapshot when the Run's caps subsequently increase.

A durable Run saves its selected inputs before work and records controller checkpoints in SQLite. Checkpoints reference existing observations and immutable arrays rather than copying a growing history. Method-owned numerical and native caches use explicit archive hooks. Loading restores those values without rebuilding eigensystems, references, circuits or selected inputs. Unchanged cache objects reuse their files after reopening. A changed cache file becomes current only when the frontier commits; superseded files are then removed.

New cache payloads use the reserved `.nwqlib-cache-` filename prefix. An interruption can leave a completed or partial file without a committed SQLite pointer. Reopening acquires the exclusive journal lock, loads the committed cache owners and their file dependencies, then removes unused files in that namespace before it counts the stored file bytes and writes any recovery revision. This order allows recovery even when unpublished files fill the allowance. Plan inputs, referenced cache files and files outside the reserved namespace are preserved. Recovery scans filenames once and uses the references gathered by ordinary cache restoration. It does not parse orphan arrays or circuits.

A controller checkpoint is one header row, holding its sequence number and field names, and one row per top-level state field. The header, the changed field rows and the RNG position commit in one transaction. `Run.checkpoint(state, changed=names)` encodes and writes only the named fields, and every other field keeps its committed row. The caller names each field that changed since its previous checkpoint, including an added or removed field. The Run rejects an unnamed added or removed field but does not compare the values of the other fields. Omitting `changed` writes every field. `run.checkpoint_state` and `RunData.controller` join the committed rows into one state. ADAPT names all of its small fields at every checkpoint. It adds the projected pencil when an analysis replaces it, and the decision history when a record is appended or the newest record is updated. A checkpoint made while acquiring one observation therefore writes that observation's pending entry and the small fields, and does not encode the pencil or the decision history again.

Each immutable native definition, lowered Aer source and prepared native handle has its own stable cache row. Their actual dictionary mutation owners record changed keys, so checkpointing does not walk prepared-handle or definition history. The active frontier has two rows, each saved only when it changes. The `frontier` row holds the current parameter specializations and backend data. Each native preparation replaces its specializations and rewrites only this small row. The `method` row holds the live method context. Each access to a method context that is not a dictionary marks the `method` row for saving at the next journal write, unless its owner marks its own changes. ADAPT marks its context after each projected analysis and when its controller returns, both for host acquisitions and for native preparations. That context holds keyed caches such as state vectors, Hamiltonian actions and compiled gates. If the process ends before the controller returns, a resumed Run recomputes at most the cache entries created after the last saved context. File references are indexed per row: successful replacement/deletion updates only those references, then removes newly unreferenced cache files. Failed publication restores changed dictionary entries, provisional file identities and their byte charges. This does not claim that every controller operation has constant cost; active-frontier traversal, explicit snapshots and once-only restoration still visit their actual population.

Collection has a separate positive ordinal in SQLite; zero means completed but uncollected. This preserves collection order independently of completion/receipt order, including when completed observations are collected in reverse order. Repeated collection keeps its original ordinal. ADAPT durable caches use the Run's canonical observations and rebuild their lookup/order once on restore, without acquisition or analysis. A standalone Result keeps its own explicit observation/context snapshot.

Current Run archives use `nwqlib.run/18`, which establishes ownership of the reserved cache filename prefix and stores a probability readout as binary arrays with its manifests and summaries in the chunk row. Each journal row stores the byte size of its JSON text in a column written with the text, and the size caps and stored-data totals read that column without reading the text. It stores, with each prepared Aer handle, the prefix phases of its saved trajectory states and its thread cap. In this format, `run.json` holds only the format, the selection file name and the limits in force when the folder was written. The journal keeps the initial limits and every later amendment. Older development formats require their original source/environment. Published numerical Artifacts have one durable payload in SQLite, committed with their manifest and completed observation. An in-memory Run saved later writes those same payload bytes and associations in one snapshot transaction. No second Artifact NPY file is written. Run loading registers each published array without reading it. Its first use reads the stored blocks once per payload digest into one read-only buffer, checking block order and byte count without recomputing the digest or scanning the values, and each manifest gets a view of its own dtype and shape. An array first used after the Run is closed is read through a read-only journal connection, and an array already read stays readable. Run loading also registers each prepared handle's saved circuit file without decoding it, and the circuit is decoded at the handle's first submission or inspection. Original Plan inputs and nonpublished method-cache arrays use their existing single-file storage. An explicit Run copy or standalone Result save is a separate requested output and may contain its own payload. Copying a durable Run whose cache rows are all committed copies the files that those rows name under the same names, without decoding or encoding the cached objects again.

`Run._write` encodes each changed row once and passes that admitted encoding to SQLite. The journal independently checks the actual transaction byte total and binary declarations. Upserts and deletions of cache rows and checkpoint fields can share one transaction, and conflicting keys are rejected before mutation. Deletion is limited to cache rows and to checkpoint fields that a controller removed from its state. Scientific observations, receipts and payload associations cannot be pruned. Live metadata byte counters change only after commit. Logical row/binary bytes and allocated database-file bytes remain distinct: deleting rows does not promise that SQLite files shrink, and checkpoints do not run VACUUM.

Acquisition admission and completion use the same JSON size owner. One count, probability or Pauli statistic supplies the per-item envelope, multiplied by the declared cardinality. Host scalar labels use their actual escaped UTF-8 lengths, and arrays use their declared byte counts. This requires no outcome enumeration. Strings have their escaped UTF-8 size, integers their decimal size, and finite binary64 values a conservative 32-byte envelope. Replaced rows receive credit for their existing encoded bytes, so a repeated batch-header update is charged for its growth.

Declared observations, bindings and register layouts have known encoded sizes and are funded exactly in the fixed reservation. So are host application receipts whose JSON size bound the kernel declares in `SelectedKernel.application_bytes`, because the Method fixes them at selection. Completion subtracts the smaller of that declaration and the returned receipts' bound before checking the variable metadata. Provider annotations and undeclared host application receipts have variable size. `ExecutionLimits.max_completion_metadata_bytes` reserves 65,536 additional bytes per acquisition for those fields, apart from declarations, statistic bodies and binary arrays. A single-endpoint probability readout reserves eight bytes per possible outcome, its declared chunk fields and one completion-metadata allowance. Before lowering and again before submission, it checks that the remaining chunk fields, the largest legal probability encoding's manifests and summaries, and the known net publication and completion-row costs fit that allowance. A backend with unbounded job text or other unbounded completion fields still checks their actual bytes when publishing the result. On Aer, counts, exact Pauli scalar and amplitude readouts check their known completion-metadata requirement against this allowance before native preparation. Another backend checks such readouts when it publishes them. A trajectory reserves each point chunk's one-point declaration, its fixed header fields and its values separately. A probability point's fixed header funds its array manifests, scalar summaries, publication-row growth and payload-reference rows at their largest legal encoding, so this allowance funds each point chunk's job text and empty values envelope and the acquisition's other completion rows. Trajectory admission reserves the backend's maximum established growth of the acquisition's completion rows. For Aer's synchronous completion rows, including revision parents, job locator, timing evidence and microsecond timestamps, the reserved growth is 1,113 bytes without a forecast and 1,044 bytes when the event already has a revision parent. For the detached completion of NWQ-Sim and its Slurm backend it is 168 bytes, or 99 bytes with a forecast. For another backend the reserved growth is temporarily zero, until a derivation of its completion lifecycle establishes the growth of its completion rows. Actual replaced rows are credited once at publication. Before native work the Run refuses a trajectory whose required envelopes exceed the allowance. Completion checks a conservative JSON bound on the variable metadata delta and names this limit when it is exceeded. The allowance can be increased with the other execution limits. It reserves storage without allocating an output buffer and does not restrict the number of declared Pauli terms.

SQLite uses local filesystem durability and a POSIX advisory lock for one active controller. Close before reopening, and keep the archive folder available for mapped arrays. A crash-left lock file is reused after its owner exits; its presence alone is not a live process. Sharing a live controller across fork, replacing files externally and distributed/network-filesystem controllers are unsupported. Failed persistence blocks further mutation rather than inventing a completion. Current extended limits load before larger checkpoint data, and accumulated work remains spent.

Cancellation prevents new work and targets original pending preparation/submission locators. Only returned provider status establishes cancellation. `resume(reanalyze=True)` is a separate explicit Method-owned recovery of interrupted classical controller analysis; ordinary resume and wait do not replay it. Recovery must preserve scientific settings, saved populations, RNG and exposure and cannot replace unresolved provider work.

RunData snapshots share immutable observations, receipts and arrays. Result context is optional and belongs to a concrete verification consumer; a Method must supply its immutable snapshot and archive hooks. The runtime never computes extra references for persistence. Completed Run load returns its saved Result without reanalysis. See [prepared execution](../prepared_execution.md) and [saved results](../saved_evidence.md) for the public workflow.

## Write order and crash windows

Every write that reserves work happens before that work starts, and every write that publishes an outcome includes all of that outcome. In-memory state changes only after the journal commit succeeds, or is restored when it fails. A static Plan has a fixed list of experiments, each prepared and acquired once by `prepare_static` and `execute_static`. `prepare_static` prepares the first experiment, or all of them for `prepare(plan, settings="all")`, and `execute_static` prepares each remaining one when it reaches it. Before its first preparation, `prepare_static` checks the readout of every experiment against the backend target and the whole Plan against the Run's cumulative limits. On Aer it also checks, before that preparation, the largest known completion-metadata requirement of all the Plan's counts, exact Pauli scalar and amplitude settings. A target refusal there names the experiment and, for a counts readout, the shots per program that it requests, or for any other readout its readout kind. One static acquisition passes through these commits, and a process can stop between any two of them:

1. **Workflow row.** The experiment's runtime seed and the RNG position commit before anything is prepared, so a restart before the preparation charge prepares the experiment with that same seed.
2. **Preparation charge and RNG position.** If the process stops after this commit and before the receipt, reopening counts a circuit preparation's charge against `max_total_circuits`. The static workflow does not rebuild a failed or interrupted preparation. The Run never repeats a preparation attempt on its own, since that would be new charged work the caller did not request. Such a Run cannot complete, so `execute_static` raises `PreparationNotRebuilt` before it submits any further experiment. After `prepare(plan, settings="all")` this row can precede experiments that were never submitted. Before lowering or the backend makes an exact dense synthesis, a revision of this charge reserves its work against `max_synthesis_work` in its own commit, so a stop during the synthesis leaves that work charged. When the limit refuses the work, the revision records the refused amount instead and, in the same commit, removes the preparation from its static workflow item or controller checkpoint. The refused preparation stays charged, and because the commit removed it from the workflow item or checkpoint, the next call of the workflow or controller prepares the experiment again, unlike after a failed or interrupted preparation.
3. **Receipt and native payload**, with the Aer handle's QPY cache row. If the process stops here, the preparation is complete on disk. A later `resume` submits the saved payload without lowering or transpiling again.
4. **Submission intent, reserved events and output reservation.** The backend is contacted only after this commit. If the process stops before an acknowledgement or outcome commits, reopening makes its reserved events `uncertain` with their shots and circuits still charged. An unacknowledged detached submission becomes `uncertain`. Recovering its original job requires a backend reconciliation path using the original submission identity. An interrupted synchronous Aer submission with no locator becomes `failed` with `results_consumed=True`, because its in-process output is unavailable, and its pending output-byte reservation is released. If the uncancelled Run has no retrievable outcome and the Method cannot return a lawful Result, `resume()` and `wait()` raise `RunFailed` at the recovery stage with status `uncertain` and the original attempt identity. The attempt stays uncertain and its exposure stays charged. A new Run is required to execute the Plan again. A synchronous backend has no acknowledgement step, so this window lasts until its outcome commits.
5. **Acknowledged locator** (detached backends). If the process stops after this commit, the submission stays `acknowledged` and its events `reserved`, and the next refresh retrieves the original job by its locator.
6. **Outcome.** For a synchronous acquisition, the completed event, the observation chunk, the submission status and any published arrays commit in one transaction, so reopening never finds one without the others. A quantum chunk was checked against its receipt when it was decoded and against its submission's job when it was published, so reopening indexes it without checking it again.
7. **Collection ordinal.** The Method's consumption of the observation is a separate commit, so the order in which a controller consumed observations survives reopening even when completion order differed.

A refresh of a detached job splits step 6. It first commits the provider's status and item associations on their own, so they survive a later decoding error. The observations then commit in a second transaction, which also sets the submission's `results_consumed` flag once the job is terminal. If the process stops between these two commits, the flag is still unset, so the next refresh reads the same job again and skips items already published.

Remote compilation follows the same intent pattern. Each upload or compile intent commits before the SDK call. The backend adapter passes the new identity to an acknowledgement callback as soon as the SDK returns it, and the callback commits it before any further work that could fail. An intent without an acknowledged identity is resolved only by reconciliation with the original preparation identity.

Cache checkpoints write new files under unused names, commit their references, and then delete files no row references. Interruption can leave unpublished or superseded cache files. Reopening removes them from the reserved cache namespace before it counts the stored file bytes. A failed commit removes provisional files, refunds their charge and restores the previous dictionary entries. This recovery contract covers process interruption and does not cover power loss.

## Lifecycle rules and their owners

| Rule | Failure it prevents | Owner |
| --- | --- | --- |
| One owner of execution and storage for each execution (one `run_id`) | Two exposure ledgers that disagree about spent work or data provenance | `_prepared_execution.Run` |
| Reserve before work | A reused random draw or a duplicate submission after a crash | `_prepared_execution.prepare_experiment`, `Run._begin_submission`, `_submit_host` |
| Publish an outcome atomically | An observation without its exposure record, or an array without its acquisition | `Run._finish_attempt`, `Run._flush_publications`, `_run_journal.LocalJournal.commit` |
| An unrecoverable outcome stays uncertain | A hidden failure, a refund or a resubmission of work the provider may have run | `Run._fail_attempt`, `Run._restore`, `Run._raise_unrecoverable_outcome` |
| Pending work keeps its locator, attempts and item ordinals, and reopening restores RNG and collection order | A replacement job or a wrong association between data and its request | `refresh_submissions`, `submit_detached`, `_remote_preparation._advance`, `Run._restore` |
| Collection order is its own ordinal | A reopened controller seeing observations in another order | `Run.collect`, `LocalJournal.commit` |
| Checkpoints write only changed fields and cache rows, atomically | Checkpoint cost growing with history, or a half-written checkpoint | `Run.checkpoint`, `_run_archive.write_caches`, `_run_archive.finish_caches` |
| Reopen restores saved state without replay | New work or changed results when a Run or Result is opened | `_run_archive.load`, `Run._restore`, `saved_evidence.load_result` |
| Idle native handles can be released | Memory held by fully collected native circuits in a long Run | `Run.release_native`, `PreparedHandle._restore_native` |
| Headers of native inputs and of a standalone Result's published arrays always checked, their values not read | Wrong reads from a corrupt header, and a full read on every load | `_choice_archive.ArchiveFiles.read_state`, `read_operator`, `saved_evidence.load_data` |
| Exact-probability unit bound checked where a chunk meets its receipt | A probability total above one beyond the roundoff of the executed circuit | `ObservationChunk.validate_unit_bound`, called by `_quantum_chunk` and, before a Result is saved, by `saved_evidence._validate_recorded_data` |
